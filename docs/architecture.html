Residence Monorepo Blueprint

Five apps, three packages, one database — how the pieces talk at runtime, how they run on your laptop, and how a push to main becomes a deployed site.

The shape of it

One repo, five deployables, no shared runtime

The repository is a monorepo, but nothing is deployed as a monolith. Each app has its own build, its own dependencies, its own config. What binds them together is not a runtime — it is a set of URLs in environment variables and a shared HTTP contract.

Web and admin now share a host: admin is built separately and nested into the web export at /admin, so both ship in one Pages artifact from one origin. Separate builds, one deploy.

apps/admin Record management — its own build, mounted at /admin Next 16, output: "export" GitHub Pages, nested

Only apps/web, apps/admin and packages/* are npm workspaces. The two native clients re-declare the entity shapes by hand in Models.swift and Models.kt — packages/contracts cannot reach them, so a contract change has to be mirrored there manually.

Runtime architecture

Auth goes straight to Supabase; data never does

This is the single most important line in the system, and it is easy to get backwards. Every client signs in against Supabase directly — the password never touches your API. But no client reads or writes data through Supabase. There is not one supabase.from(...) call anywhere in the codebase; every data path goes through FastAPI, which verifies the resulting JWT.

Three surfaces, three data paths

  • Web 1.0 (/1.0/**) reads the typed seed through lib/repository.ts at build time. It hits neither Supabase nor the API at runtime — it is pure static HTML.
  • Web 2.0 and the portal fetch live at runtime. 2.0 takes the project from the URL; the portal pins PORTAL_PROJECT_ID.
  • Admin fetches live at runtime against a project you select, persisted under portal_selected_project.
Why the RLS change was safe Enabling row-level security with no policies shut the PostgREST door — and nothing was using that door. The API connects as postgres, which bypasses RLS, which is why every endpoint kept working. What changed is that the anon key shipped in your JS bundle is now auth-only, instead of also being a live read/write handle on all 22 unprotected tables.
The boundary is the API, never the UI Both web apps are static exports with no server, so there is no middleware and the page markup is a public file on a CDN. V2AuthGate and the admin's AuthGate decide what a browser renders; require_user decides what anyone can reach. Anything sensitive must arrive from a gated endpoint at runtime — never be baked into data/*.ts.

Local development

One launcher, and it points at production data by default

./scripts/dev.sh starts everything from the repo root. It refuses to start when a port is taken and names the offending PID, because a stale server on :3000 looks exactly like code that will not reload.

The default is not a sandbox DB_TARGET defaults to supabase because that is the database the apps are actually developed against. The trade is real: local dev writes to the same Postgres production reads. Auth is real too, so unauthenticated calls 401 exactly as they would in production.

Migrations

The schema is Alembic, in apps/api/migrations/versions/, with the original SQL kept for reference under migrations/raw/. Nothing runs migrations automatically — applying one to Supabase is a deliberate manual act from your machine:

StepCommand
Load cloud envcd apps/api && set -a && . ./.env.supabase && set +a
Apply./.venv/bin/alembic upgrade head
Inspect./.venv/bin/alembic current

Note that migrations/env.py carries the same three connect_args as app/shared/db.py — Supabase's transaction pooler reuses one server connection across yours, so prepared-statement caching and fixed statement names both have to be off.

Production

Two hosts, one shared database

Nothing in production runs Node. Both frontends are static files served from a single Pages origin; the only server-side code anywhere is the FastAPI instance on Render.

The env vars that actually break things NEXT_PUBLIC_* values are inlined at build time, so changing one in a host dashboard does nothing until you rebuild — moving the API to a new host means rebuilding both frontends, not just repointing DNS. ADMIN_BASE_PATH is the other one that matters: without it the nested admin build requests /_next/… and is served the web app's chunks.

GitHub & deployment

What a push actually triggers

Three workflows, and they deliberately do not overlap. CI never runs on main; the deploys only run on main.

WorkflowFires onDoesGate
ci.yml every branch except main, plus every PR typecheck:all · vitest · ruff · mypy · OpenAPI export · npm run verify always
deploy.yml push to main (any path) pre-warm API → build web → build admin with ADMIN_BASE_PATH=/admin → nest into apps/web/out/admin → Pages always
— none — the API Render deploys from its own git integration, per render.yaml outside Actions

The web deploy, step by step

  1. Push lands on main CI does not run here — it ran on the branch and the PR. deploy.yml and possibly deploy-admin.yml start in parallel, each with its own concurrency group so deploys serialize rather than cancel each other.
  2. Pre-warm the API A best-effort curl to $API_BASE_URL/healthz with retries, to wake the sleeping Render instance before any build-time fetch needs it.
  3. Build apps/web With DATA_SOURCE unset the public pages build from the local seed — zero config, always green. Set the repo variable to api and they build from live data instead, with ALLOW_SEED_FALLBACK=1 so an unreachable API degrades to the seed rather than failing the deploy.
  4. Build the admin app under /admin A second, independent Next build with ADMIN_BASE_PATH=/admin, which prefixes every route and every asset URL. Its NEXT_PUBLIC_* values are set separately from the web build's.
  5. Nest one export into the other apps/admin/out is copied to apps/web/out/admin, guarded by a check that the path does not already exist — if it does, the two builds are fighting over the same route and the deploy fails rather than publishing something half-built.
  6. Publish to Pages The combined apps/web/out is uploaded and deployed. One artifact, one origin, both apps.

Where it bends

Seams worth knowing before you change something

  • Web and admin now share a browser origin. They are still separate builds, but they share localStorage and therefore the Supabase session — signing in on the public app also signs you into /admin. That is effectively single sign-on; require_admin still decides what the session can reach.
  • The seed is still the source of record for media. data/renderings.ts and data/drawingSheets.ts flow into the database through npm run export:seed and scripts/seed.py, with ids derived from kind plus owner slug plus index — so re-seeding upserts rather than duplicates.
  • Native clients drift silently. A change to packages/contracts compiles both web apps and reaches neither Models.swift nor Models.kt. Nothing fails; the apps just decode the old shape.
  • Every entity carries a required projectId. Collection GETs accept ?projectId=, and omitting it returns every project's rows — so a caller rendering one project must always pass it. Slugs are unique per project, not globally.
  • Role lives in app_metadata, never user_metadata. Only the service_role key can write it. user_profiles.role is a mirror for display; PATCH /me accepts displayName and nothing else, because a role field there would be self-promotion.
  • There is no per-user project membership. New signups get viewer, which means read access to every project. That is the open tenancy question, not a bug in a specific endpoint.
  • Uploads need a real Drive owner. A service account has no storage of its own, so GOOGLE_DRIVE_FOLDER_ID must name a folder owned by a person and shared with the service account as Editor — without it, the upload endpoints return 501.
