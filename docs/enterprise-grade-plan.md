## 1. The enterprise blockers, ranked

### 🔴 B1 — The tenant boundary is a query parameter, not an enforced boundary

This is the single most important finding.

`project_id` now exists on every row. But nothing *enforces* it. In `app/shared/crud.py:182`,
the list endpoint takes the tenant from the caller:

```python
project_id: str | None = Query(None, alias="projectId",
    description="Restrict to one project. Omitted returns every project's rows.")
```

And authorization (`require_user` / `require_admin`) resolves a **global** role. There is no
organisation, no membership table, no per-project grant — `grep -rni "organization\|org_id\|
membership" app/` returns only comments.

The consequence, stated plainly: **any authenticated admin can read and write every tenant's
data, and any authenticated viewer can read every tenant's data, simply by omitting or changing
`?projectId=`.** The project picker in 2.0 and admin is a client-side filter over a shared pool.
CLAUDE.md itself documents the hazard ("omitting it returns every project's rows, so a caller
that renders one project must always pass it") — but a security boundary that depends on callers
remembering to pass a parameter is not a boundary.

Retrofitting tenancy after real customer data exists is the most expensive migration in SaaS.
Do it before customer #2, not after.

### 🔴 B2 — Postgres tables are world-readable past the API

CLAUDE.md is explicit and correct: `user_profiles` has RLS enabled with no policies, and **"the
other tables do not have this yet and remain exposed the same way."** Supabase publishes every
`public` table through PostgREST, reachable with the anon key that ships in the browser bundle.

So every BOQ, quote, vendor rate and payment figure in the database is readable by anyone who
opens devtools on the public site. The API's `require_user` guards the API — it does not guard
the database. This is a live data exposure the moment real commercial figures land.

### 🔴 B3 — A tenancy regression shipped in the Alembic conversion

Constitution rule 5 says slugs are unique **per project**. The initial autogenerated migration
inverted that (`migrations/versions/f5201d681403_initial_models.py:55-58`):

```python
op.drop_constraint(op.f('domains_project_id_slug_key'), 'domains', type_='unique')
op.create_unique_constraint(None, 'domains', ['slug'])
op.drop_constraint(op.f('spaces_project_id_slug_key'), 'spaces', type_='unique')
op.create_unique_constraint(None, 'spaces', ['slug'])
```

The ORM matches (`SpaceModel.slug`, `DomainModel.slug` both `unique=True`). Effect: **the second
customer cannot create a space called `master-bedroom`,** because the first customer has it. A
global unique on a per-tenant natural key is a classic multi-tenancy defect, and this one is a
regression from the hand-written SQL that had it right.

Fix: composite `UniqueConstraint("project_id", "slug")` on both models, plus an Alembic revision.
This is a one-hour fix and should happen this week.

### 🟠 B4 — No audit trail

`grep -rn "created_at\|updated_at\|created_by"` across the ORM models returns **nothing**. No
row knows when it was created, when it last changed, or who changed it.

For a documentation site, fine. For a system holding BOQ line items, negotiated quotes, purchase
orders and payment milestones, "who approved this ₹18L quote and when" is not a nice-to-have —
it is the reason the system is trusted at all. Disputes are the normal case in construction, not
the exception. A platform that cannot answer that question loses every dispute it is cited in.

### 🟠 B5 — No delete, no archive, no lifecycle

The generic CRUD factory has `list / get / create / update` and no delete path at all
(`grep -rn "delete" app/shared/crud.py` → no matches). Rows are immortal. There is no soft
delete, no archive, no retention policy, no tenant offboarding story, and therefore no answer to
a customer asking for their data to be removed.

### 🟠 B6 — No pagination

`GET /<collection>` returns every row for the whole tenant (or every tenant). One project with a
full BOQ is a few hundred rows. Fifty projects with photo-heavy progress logs is not. There is
no `limit`, no `offset`, no cursor, no cap. This degrades silently and then falls over.

### 🟠 B7 — The API is effectively unobserved and unprotected

`grep -rn "logger\|sentry\|opentelemetry\|slowapi\|limiter" app/` finds **one** logger, in the
notification stub. That means:

- No structured request logging, no request/correlation IDs
- No error tracking — a 500 in production is invisible unless a user reports it
- No metrics, no tracing, no latency or error-rate SLOs
- **No rate limiting anywhere** — including on the auth-adjacent and upload endpoints

### 🟡 B8 — File storage is Google Drive on a personal account

`app/shared/drive.py` + the config comments are candid: a service account has no storage quota,
so uploads run on an **OAuth user token belonging to a real person's @gmail.com Drive**, and
`GOOGLE_DRIVE_PUBLIC` grants `anyone: reader` to make files renderable.

For an enterprise deliverable that is three problems at once: the storage is owned by an
individual rather than the company, there is no per-tenant isolation, and "public link" is the
only sharing model — no signed, expiring, access-checked URLs. Customer drawings and contracts
cannot live there.

### 🟡 B9 — Test coverage is near zero where the money is

Two vitest files exist, both in `packages/api-client`. There is **no pytest suite** — the
`commercial` context (quotes, BOQ line items, purchase orders, deliveries, the approve/negotiate/
reject workflow) is the richest and most consequential code in the repo and has no tests at all.
CI runs lint and typecheck, which catch shape errors, not logic errors.

### 🟡 B10 — No API versioning or contract enforcement

Routes are unversioned (`/projects`, not `/v1/projects`). Three independent clients — web, admin,
and two native apps that **hand-copy the entity shapes** into `Models.swift` / `Models.kt` — will
break silently on any field rename. CI exports the OpenAPI schema but does not diff it against
the committed baseline, so a breaking change passes green.

### 🟡 B11 — Release hygiene

The working tree carries **80+ uncommitted modified/deleted files**, including a wholesale
deletion of `apps/mobile` and of all four raw SQL migrations. That is a large, unreviewed,
unbisectable change sitting outside version control. Enterprise-grade starts with "every change
is a reviewed commit."

## 2. The tenancy model to build (B1, concretely)

The recommendation is a standard three-table model, plus enforcement in one place.

```
organizations        id, name, created_at
memberships          org_id, user_id, role (owner|admin|member|viewer), UNIQUE(org_id,user_id)
projects             + org_id  ← the tenant root gains an owner
```

Every existing entity keeps `project_id`; the org is reached through the project. Then:

1. **Resolve the tenant server-side, never from a query param.** A `TenantContext` dependency
   takes the verified JWT `sub`, loads the user's memberships, and produces the set of project
   ids they may touch. `list_all()` filters by that set. `?projectId=` becomes a *narrowing*
   filter within the permitted set, and an id outside the set is a 404, not a 403 (don't leak
   existence).
2. **Roles become per-org, not global.** `require_admin` becomes `require_project_role(project_id,
   "admin")`. The current global `app_metadata.role` survives only as a platform-staff superuser
   flag, and should be renamed to make that explicit.
3. **Defence in depth: enable RLS on every table** with a policy keyed to the membership table.
   The API connects as `postgres` and bypasses RLS, so this costs nothing at runtime — it exists
   precisely to close B2, the PostgREST anon-key path. Do this even though the API filters
   correctly, because one forgotten `.filter()` should not be a breach.
4. **Prove it with tests.** A cross-tenant test fixture (org A, org B, one user in each) asserting
   404/403 on every collection endpoint is the single highest-value test suite in the repo.

Sequencing matters: build 1 and 2 together, ship 3 in the same release, and do not accept a
second customer until 4 is green.

### Phase 3 — Make it auditable (4–6 weeks) — *this is the construction-specific moat*

An append-only `audit_events` table (actor, org, project, entity, action, before/after diff,
timestamp) written by the service layer, not by triggers, so it captures intent.

Then the domain events that actually matter in construction, on top of it:

- **Quote approval chain** — who approved, at what figure, against which BOQ line, when
- **Change orders as first-class entities** — a scope change is not a PATCH to a BOQ row; it is a
  new record with cause, cost delta, schedule delta, and an approver. This is where projects
  actually go wrong, and no owner-side tool in India models it.
- **Payment milestones** tied to verified progress entries, not to dates
- **Snag/defect lifecycle** with liability period and warranty linkage — you already have
  `handover`/`Warranty`, it just isn't connected to the clock

Immutable history is what turns this from a nicer spreadsheet into the artifact that settles a
dispute. It is also the thing a builder cannot replicate by adding a feature, because it requires
having been trustworthy from day one.

### Phase 4 — Make it enterprise-sellable (ongoing)

SSO/SAML, SCIM provisioning, configurable data residency (India — meaningful under the DPDP Act),
DPA and subprocessor list, SOC 2 Type I readiness, documented RTO/RPO, and a status page. None of
this is engineering-hard; all of it is procurement-blocking, and it is all cheaper to design for
in Phase 1 than to bolt on later.

## 4. Product ideas that follow from the architecture you already have

The July review named the wedge correctly — owner-side advocacy, cost benchmarking, regulatory
depth. Three concrete additions from this pass, each cheap *because* of decisions already made:

1. **Benchmark-on-quote.** You will hold real BOQs and real quotes across projects. The moment
   there are ~20, "this vendor's tile-laying rate is 34% above the Bengaluru median for this
   spec" is a single query and the most valuable sentence the product can say to an owner. It
   requires nothing but the tenancy work — the data model is already there. Note the tension:
   cross-tenant aggregates must be built on explicitly consented, anonymized, k-anonymous
   extracts, decided in Phase 1 rather than discovered later.

2. **The handover dossier as the retention hook.** `handover` + `document` + `media` already hold
   drawings, warranties and as-builts. One button producing a complete, permanent, shareable home
   record — warranties with expiry alerts, as-built drawings, vendor contacts, material specs —
   is the artifact an owner still opens in year seven. It converts a project tool into a
   relationship, and `app/shared/pdf.py` means you are part-way there.

3. **Contract-first native clients.** `packages/contracts` cannot reach `Models.swift` /
   `Models.kt`, so today a field rename silently breaks two apps. Generate those from the OpenAPI
   schema in CI instead. Small piece of work; removes an entire class of production bug across
   four clients.
